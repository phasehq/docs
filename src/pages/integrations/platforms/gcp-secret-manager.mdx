# GCP Secret Manager

You can use Phase to sync secrets to Google Cloud Secret Manager. Phase supports two sync modes:

- **One secret per key**: Each Phase secret becomes its own Secret Manager secret, named after its key. This is how Cloud Run, Cloud Run functions, GKE and the Google Cloud client libraries read secrets.
- **Single JSON secret**: All Phase secrets are synced as one JSON object to a single Secret Manager secret, like the AWS Secrets Manager integration.

Phase authenticates with [Workload Identity Federation](https://cloud.google.com/iam/docs/workload-identity-federation). No service account key is created, and Phase Cloud and self-hosted instances are set up the same way, with nothing to configure on the instance.

<DocActions />

### Prerequisites

- A Google Cloud project with billing enabled
- The `gcloud` CLI, or [Cloud Shell](https://shell.cloud.google.com/?show=terminal)
- Permission to enable APIs, create Workload Identity pools and grant IAM roles in the project, for example the Owner role, or IAM Workload Identity Pool Admin, Project IAM Admin and Service Usage Admin

<Warning>
  When secret syncing is enabled, secrets stored inside Phase are treated as the
  source of truth. Secrets in Google Cloud with the same names are
  **overwritten**, secrets that Phase created are **disabled** when their keys
  are removed from Phase, and versions older than the previous one are
  **destroyed**. Import your existing secrets into Phase before continuing. See
  [Import existing secrets from GCP Secret
  Manager](#optional-import-existing-secrets-from-gcp-secret-manager-into-phase).
</Warning>

## How authentication works

1. When you create a Google Cloud credential, Phase generates an RSA signing key for that credential only. The private key never leaves Phase.
2. You upload the public half, a JSON Web Key Set (JWKS), to a Workload Identity pool provider in your project. Google never contacts Phase to fetch it, so this also works for self-hosted instances on private networks.
3. When a sync runs, Phase signs a token that expires in an hour, exchanges it with Google's Security Token Service for an access token that expires with it, and calls Secret Manager as the principal `principal://iam.googleapis.com/projects/PROJECT_NUMBER/locations/global/workloadIdentityPools/phase/subject/SUBJECT`.

Google never issues Phase a long-lived credential, so there's nothing on the Google side to rotate or leak. Because each credential has its own key, a provider you create for one credential can't be used by any other Phase credential or organisation.

<Note>
  Why not a service account key? Google Cloud organizations created since May
  2024 block service account key creation and key upload by default
  (`iam.managed.disableServiceAccountKeyCreation` and
  `iam.disableServiceAccountKeyUpload`), and only an organization-level admin
  can lift that. Workload Identity Federation isn't affected.
</Note>

## Set up Google Cloud credentials in Phase

### Step 1: Start a new credential

1. Go to **Integrations** from the sidebar and click on **Third-party credentials**.

![Go to integrations](/assets/images/platform-integrations/integrations-sidebar.png)

2. Click on **Google Cloud**. Phase generates a signing key for the new credential.

3. Enter the **project number** of the Google Cloud project that will hold the Workload Identity pool. Use **List your projects in the Google Cloud console** to find it: open the project and its dashboard shows the project ID and number. Google identifies Workload Identity providers by project number, not ID, and Phase picks the pool and provider IDs, so the number is all Phase needs to complete the setup.

### Step 2: Add the Phase public key to your Workload Identity Pool

Pick one of the three ways below. They all create the same resources.

<TabGroup>
  <TabPanel title="Setup script (recommended)" slug="setup-script">

The script is shown in a tab per Phase integration. Pick the **GCP Secret Manager** tab, click **Copy**, and run it in [Cloud Shell](https://shell.cloud.google.com/?show=terminal), or in any terminal where `gcloud` is signed in to the project. It looks like this, with this credential's values filled in:

```fish
(
set -euo pipefail
PROJECT_NUMBER='123456789012'
POOL_ID='phase'
PROVIDER_ID='phase-3f9a1b2c'
ISSUER='https://console.phase.dev'
SUBJECT='phase:org:ORG_ID:key:3f9a1b2c...'
PRINCIPAL="principal://iam.googleapis.com/projects/$PROJECT_NUMBER/locations/global/workloadIdentityPools/$POOL_ID/subject/$SUBJECT"

gcloud services enable iam.googleapis.com sts.googleapis.com cloudresourcemanager.googleapis.com \
  secretmanager.googleapis.com --project="$PROJECT_NUMBER"
# gcloud's Workload Identity commands take the project ID, not the number.
PROJECT_ID="$(gcloud projects describe "$PROJECT_NUMBER" --format='value(projectId)')"

# Phase's public key for this credential.
printf '%s\n' '{
  "keys": [
    {
      "kty": "RSA",
      "alg": "RS256",
      "use": "sig",
      "kid": "3f9a1b2c...",
      "n": "...",
      "e": "AQAB"
    }
  ]
}' > phase-jwks.json

POOL_STATE="$(gcloud iam workload-identity-pools describe "$POOL_ID" --location=global \
  --project="$PROJECT_ID" --format='value(state)' 2>/dev/null || true)"
if [ -z "$POOL_STATE" ]; then
  gcloud iam workload-identity-pools create "$POOL_ID" --location=global \
    --project="$PROJECT_ID" --display-name="Phase"
elif [ "$POOL_STATE" = "DELETED" ]; then
  gcloud iam workload-identity-pools undelete "$POOL_ID" --location=global \
    --project="$PROJECT_ID"
fi

PROVIDER_STATE="$(gcloud iam workload-identity-pools providers describe "$PROVIDER_ID" \
  --location=global --workload-identity-pool="$POOL_ID" --project="$PROJECT_ID" \
  --format='value(state)' 2>/dev/null || true)"
if [ "$PROVIDER_STATE" = "DELETED" ]; then
  gcloud iam workload-identity-pools providers undelete "$PROVIDER_ID" \
    --location=global --workload-identity-pool="$POOL_ID" --project="$PROJECT_ID"
fi
if [ -z "$PROVIDER_STATE" ]; then ACTION=create-oidc; else ACTION=update-oidc; fi
gcloud iam workload-identity-pools providers "$ACTION" "$PROVIDER_ID" \
  --location=global --workload-identity-pool="$POOL_ID" --project="$PROJECT_ID" \
  --display-name="Phase" --issuer-uri="$ISSUER" --jwk-json-path=phase-jwks.json \
  --attribute-mapping="google.subject=assertion.sub" \
  --attribute-condition="assertion.sub == \"$SUBJECT\""

for ROLE in roles/secretmanager.editor roles/secretmanager.secretAccessor; do
  gcloud projects add-iam-policy-binding "$PROJECT_ID" --role="$ROLE" \
    --member="$PRINCIPAL" --condition=None >/dev/null
done

echo "Done: Google Cloud now trusts this Phase integration."
)
```

The script:

1. Enables the IAM, Security Token Service, Resource Manager and Secret Manager APIs, and looks up the project ID from the number (gcloud's Workload Identity commands only accept the ID).
2. Creates a Workload Identity pool named `phase` if the project doesn't have one yet. Every Phase credential in the project can share it.
3. Creates an OIDC provider for this credential that trusts only its public key, and only tokens for its subject.
4. Grants that subject the two Secret Manager roles described in [Permissions](#permissions).

It's safe to run again: it restores a pool or provider deleted in the last 30 days, and brings an existing provider back in line with the credential. It runs in a subshell that stops at the first error, so a failure never closes your Cloud Shell session.

  </TabPanel>
  <TabPanel title="Cloud console" slug="cloud-console">

Use exactly the pool ID `phase` and the provider ID Phase shows (for example `phase-3f9a1b2c`): Phase builds the provider name from them and your project number.

1. In Phase, click **Copy JWKS** and save it to a file named `phase-jwks.json`.
2. In the Google Cloud console, open **IAM & Admin** > **Workload Identity Federation** and click **Create pool**. Give it the ID `phase`.
3. Add a provider to the pool:
   - **Select a provider**: OpenID Connect (OIDC)
   - **Provider ID**: the provider ID shown in Phase, e.g. `phase-3f9a1b2c`
   - **Issuer (URL)**: the `--issuer-uri` value from the script, e.g. `https://console.phase.dev`
   - **JWK file (JSON)**: upload `phase-jwks.json`
   - **Audiences**: Default audience
4. Configure the provider attributes:
   - **Attribute mapping**: `google.subject` = `assertion.sub`
   - **Attribute condition**: the `--attribute-condition` value from the script, e.g. `assertion.sub == "phase:org:ORG_ID:key:3f9a1b2c..."`
5. Open **IAM & Admin** > **IAM**, click **Grant access**, and add the script's `PRINCIPAL` value, with your project number and the pool ID filled in. Give it the **Secret Manager Editor** and **Secret Manager Secret Accessor** roles.

  </TabPanel>

Save the JWKS from Phase (**Copy JWKS**) as `phase-jwks.json` next to your configuration, and replace the subject, issuer and provider ID with the values from the script. Keep the pool ID `phase`:

```hcl
locals {
  phase_subject = "phase:org:ORG_ID:key:3f9a1b2c..."
}

resource "google_iam_workload_identity_pool" "phase" {
  workload_identity_pool_id = "phase"
  display_name              = "Phase"
}

resource "google_iam_workload_identity_pool_provider" "phase" {
  workload_identity_pool_id          = google_iam_workload_identity_pool.phase.workload_identity_pool_id
  workload_identity_pool_provider_id = "phase-3f9a1b2c"
  display_name                       = "Phase"
  attribute_mapping                  = { "google.subject" = "assertion.sub" }
  attribute_condition                = "assertion.sub == \"${local.phase_subject}\""

  oidc {
    issuer_uri = "https://console.phase.dev"
    jwks_json  = file("${path.module}/phase-jwks.json")
  }
}

resource "google_project_iam_member" "phase" {
  for_each = toset(["roles/secretmanager.editor", "roles/secretmanager.secretAccessor"])
  project  = "my-project"
  role     = each.value
  member   = "principal://iam.googleapis.com/${google_iam_workload_identity_pool.phase.name}/subject/${local.phase_subject}"
}

```

### Step 3: Verify and save

Give the credential a descriptive name and click **Verify and save**. There's nothing to copy back from Google Cloud: Phase already knows the provider's name.

Google doesn't check an uploaded JWKS when the provider is created, so Phase verifies the setup by exchanging a real token with Google before saving. If verification fails, the error from Google is shown; see [Troubleshooting](#troubleshooting).

If someone else will run the script, for example a Google Cloud admin, copy it first, then click **Save anyway** once verification fails. The script isn't shown again after you save. IAM changes can also take a few minutes to apply, so if you just ran the script, wait a moment and click **Verify and save** again.

The credential's page in Phase shows its workload identity provider and the public key (JWKS) Phase signs with, so you can match it to the provider in Google Cloud.

### Permissions

The setup grants two predefined roles:

| Role | Why Phase needs it |
| --- | --- |
| `roles/secretmanager.editor` | Create secrets, add versions, update labels and encryption settings, and disable or destroy versions. It can't change IAM policies. |
| `roles/secretmanager.secretAccessor` | Read a secret's current value, so Phase only adds a version when the value actually changed. |

Phase never deletes secrets. For a narrower grant, create a custom role with exactly the permissions Phase uses and grant it instead of the two roles above:

```fish
gcloud iam roles create phaseSecretSync --project="$PROJECT_ID" --title="Phase secret sync" \
  --permissions=secretmanager.secrets.list,secretmanager.secrets.get,secretmanager.secrets.create,secretmanager.secrets.update,secretmanager.versions.add,secretmanager.versions.access,secretmanager.versions.list,secretmanager.versions.disable,secretmanager.versions.destroy
```

### Other projects

A credential's setup covers the project that holds its Workload Identity pool. To sync to another project, create another Google Cloud credential for that project.

## Sync Secrets from Phase

### Step 1: Choose a destination

1. Enable Server-side Encryption (SSE) for the App from the [Settings](/console/apps#enabling-sse) tab if not enabled already.

2. Go to your App in the Phase Console and open the **Syncing** tab. Select **GCP Secret Manager** under the 'Create a new Sync' menu.

3. Select your Google Cloud credential. The **Project** defaults to the project that holds the credential's Workload Identity pool, where the setup script granted access.

4. Choose a **Location**:
   - **Global (automatic replication)**: Google chooses where replicas are stored.
   - **A region or multi-region** (e.g. `europe-west4`, `us`, `eu`): a [regional secret](https://cloud.google.com/secret-manager/regional-secrets/regional-secrets-overview), stored and served only in that location through its regional endpoint. Use this for data residency.

5. Click **Next**. Phase lists the project's secrets to check that it has access.

<Note>
  If Phase can't access the project, the error from Google is shown. IAM
  changes can take a few minutes to take effect.
</Note>

### Step 2: Configure the sync

1. Choose the Phase **Environment** and **Path** as the source for secrets.

2. Choose how secrets are mapped:

<TabGroup>
  <TabPanel title="One secret per key" slug="one-secret-per-key">

Each Phase secret becomes a Secret Manager secret with the same name, plus an optional **prefix**, so several environments can share a project:

| Phase key | Prefix | Secret Manager secret |
| --- | --- | --- |
| `DATABASE_URL` | none | `DATABASE_URL` |
| `DATABASE_URL` | `PROD_` | `PROD_DATABASE_URL` |
| `stripe-key` | `staging-` | `staging-stripe-key` |

Secret names may only contain letters, numbers, hyphens (`-`) and underscores (`_`), up to 255 characters including the prefix. Phase doesn't rename keys: if any key doesn't fit, for example `spring.datasource.url`, the sync fails before writing anything and lists the keys to rename.

Reference the synced secrets by name, using the `latest` version so updates from Phase are picked up. For example, on Cloud Run:

```fish
gcloud run deploy my-service --image=IMAGE \
  --set-secrets=DATABASE_URL=DATABASE_URL:latest
```

  </TabPanel>
  <TabPanel title="Single JSON secret" slug="single-json-secret">

All secrets are stored as one JSON object in a single secret. Create a new secret or pick an existing one:

```json
{
  "API_KEY": "sk-...",
  "DATABASE_URL": "postgres://...",
  "SECRET_TOKEN": "abc123"
}
```

Your application reads and parses the JSON, for example:

```fish
gcloud secrets versions access latest --secret=my-app-production | jq -r .DATABASE_URL
```

Google caps a secret at 64 KiB, so this mode suits environments with a moderate number of secrets. If the JSON would be larger, the sync fails before writing anything.

  </TabPanel>
</TabGroup>

3. Optionally, enter a **Customer-managed encryption key**. Phase then shows a script that gives your project's Secret Manager service agent access to the key. Run it before you create the sync. See [Encrypt secrets with a customer-managed key](#advanced-encrypt-secrets-with-customer-managed-encryption-keys-cmek).

4. Confirm that you understand how Phase will overwrite, disable and prune secrets, then click **Create**. The sync starts right away, and runs again whenever secrets change in Phase.

## How syncing works

- **Ownership:** Phase labels every secret it writes with `managed_by=phase` and `phase_sync=SYNC_ID`. It only ever disables secrets that carry its own sync's label, so secrets created outside Phase are never disabled.
- **Existing secrets:** A secret with the same name that was created outside Phase is adopted: Phase adds its labels (keeping yours) and a new version. A secret labelled by a *different* Phase sync is left untouched and reported in the sync log, unless that sync has been deleted: a sync's options can't be edited, so a sync you delete and recreate takes over the secrets its predecessor wrote.
- **Changes:** Phase compares each value with the secret's current version and only adds a version when the value changed.
- **Versions:** Phase keeps the current and the previous version of each secret, like AWS Secrets Manager's `AWSCURRENT` and `AWSPREVIOUS`, and destroys older versions, because Google bills every version that isn't destroyed. If a secret has [delayed destruction](https://cloud.google.com/secret-manager/docs/delay-destruction-of-secret-versions) configured, Google honours it. Reference `latest` rather than pinning version numbers.
- **Removed keys:** When a key is removed from Phase, Phase disables every version of the secret it created for that key and labels it `phase_removed=true`, so later syncs skip it without reading its versions. Reading `latest` then fails, so stale values aren't served, while the secret and its IAM bindings stay in place. If the key is added back, Phase adds a new, enabled version and clears the label.
- **Empty values:** Google doesn't allow empty secret values, so a key with an empty value is treated as removed, and listed in the sync log.
- **Deleting a sync** in Phase leaves the secrets in Google Cloud as they are.

## Limits & Behavior

| Limit | Value | What Phase does |
| --- | --- | --- |
| Secret name | Letters, numbers, `-` and `_`, up to 255 characters | Checks every name, including the prefix, before syncing |
| Secret value | 64 KiB per version | Checks every value (or the whole JSON) before syncing |
| Empty values | Not allowed | Treats the key as removed |
| Write requests | 600 per minute per project, shared with everything else in the project; about 2 per second per secret | Spaces out its requests and retries rate-limit errors with backoff. A new key takes two writes, so a first sync of a few hundred keys can take a few minutes. |
| Read requests | 600 per minute per project; value reads have a separate 90,000 per minute quota | Lists secrets once per sync |

Any other error from Google, for example a disabled API, a missing permission or an organization policy, is shown in the sync log with Google's message.

## Advanced: Encrypt secrets with customer-managed encryption keys (CMEK)

Secret Manager encrypts secrets with Google-managed keys by default. To use your own [Cloud KMS](https://cloud.google.com/secret-manager/docs/cmek) key, enter its full name when creating the sync, e.g. `projects/my-kms-project/locations/global/keyRings/my-ring/cryptoKeys/my-key`.

- For **global** secrets, the key must be in the `global` location.
- For **regional** secrets, the key must be in the same location as the secret, e.g. a key in `europe-west4` for secrets in `europe-west4`.

Unlike AWS, Phase's credential doesn't need any Cloud KMS permissions. Secret Manager encrypts and decrypts with the key through the project's Secret Manager service agent, so that agent needs the **Cloud KMS CryptoKey Encrypter/Decrypter** role on the key. When you enter a key, Phase shows a script that grants it. To run the commands yourself:

```fish
# Creates the service agent if it doesn't exist yet.
gcloud beta services identity create --service=secretmanager.googleapis.com --project="$PROJECT_ID"

gcloud kms keys add-iam-policy-binding projects/my-kms-project/locations/global/keyRings/my-ring/cryptoKeys/my-key \
  --member="serviceAccount:service-$PROJECT_NUMBER@gcp-sa-secretmanager.iam.gserviceaccount.com" \
  --role=roles/cloudkms.cryptoKeyEncrypterDecrypter --condition=None
```

If the service agent can't use the key, the sync stops at the first secret, and the sync log shows these commands filled in for your project and key.

New secrets are created with the key. Existing secrets that the sync manages are switched to it, and Google applies the new key to versions added from then on. Secrets that use user-managed replication keep their own keys, with a warning in the sync log.

If your organization enforces `constraints/gcp.restrictNonCmekServices` for Secret Manager, set a key on the sync, or Google will reject the secrets Phase creates.

## Self-hosted Phase

There's nothing extra to configure: no Google Cloud credentials or environment variables on the instance.

- The token issuer is your instance's URL: the first `ALLOWED_ORIGINS` entry (`${HTTP_PROTOCOL}${HOST}` by default), as https. It's fixed when each credential is created. Google only compares it with the provider's issuer and never contacts it, so a private hostname works.
- The instance needs outbound HTTPS access to `sts.googleapis.com`, `secretmanager.googleapis.com`, and for regional secrets `secretmanager.LOCATION.rep.googleapis.com`.
- If your organization restricts Workload Identity providers with the `iam.workloadIdentityPoolProviders` organization policy, allow your instance's issuer URL.

## Optional: Import existing secrets from GCP Secret Manager into Phase

If you have existing secrets you want to manage with Phase, export them to a `.env` file and import them.

1. Export the latest version of each secret. Values that span several lines need to be quoted in the file by hand:

```fish
for name in $(gcloud secrets list --project=my-project --format='value(name)'); do
  echo "$name=$(gcloud secrets versions access latest --secret=$name --project=my-project)" >> .env
done
```

2. Import secrets into Phase via the `phase-cli`:

```fish
phase secrets import .env --env development
```

3. Delete the `.env` file:

```fish
rm .env
```

## Troubleshooting

### "Google Cloud rejected Phase's Workload Identity token"

Phase shows Google's reason after the colon:

| Google's reason | Fix |
| --- | --- |
| `Invalid JWT signature` or an unknown `kid` | The provider doesn't have this credential's public key. Update it with the JWKS from the credential's page in Phase (see below). |
| `The issuer in ID Token ... does not match the expected ISSUER` | The provider's issuer URI doesn't match this Phase instance. Create a new credential and run its setup script. |
| `The target service indicated by the "audience" parameters is invalid` or `The audience in ID Token ... does not match the expected audience` | The provider Phase expects doesn't exist yet or has a different name: check the project number, and that the pool ID is `phase` and the provider ID matches the one Phase showed. You can correct the provider name on the credential's page. |
| `The given credential is rejected by the attribute condition` | The provider was set up for a different credential. Create a new credential and run its setup script. |
| Workload identity pool or provider disabled or deleted | Re-enable it, or run the credential's setup script again if you kept a copy: it restores anything deleted in the last 30 days. Otherwise create a new credential. |

To inspect the provider, or replace its key with the one in `phase-jwks.json`:

```fish
gcloud iam workload-identity-pools providers describe PROVIDER_ID \
  --workload-identity-pool=phase --location=global --project=my-project

gcloud iam workload-identity-pools providers update-oidc PROVIDER_ID \
  --workload-identity-pool=phase --location=global --project=my-project \
  --jwk-json-path=phase-jwks.json
```

### Permission denied

The credential's principal needs `roles/secretmanager.editor` and `roles/secretmanager.secretAccessor` on the project you're syncing to; the setup script grants both in the credential's project. If you're syncing to a different project, create a credential for that project instead. IAM changes can take a few minutes to take effect.

To check the current grants:

```fish
gcloud projects get-iam-policy my-project \
  --flatten="bindings[].members" \
  --filter="bindings.members:principal://iam.googleapis.com/" \
  --format="table(bindings.role, bindings.members)"
```

### The Secret Manager API is disabled

The sync log includes a link to enable the API for the project. Or run:

```fish
gcloud services enable secretmanager.googleapis.com --project=my-project
```

### Blocked by an organization policy

Errors that mention a constraint, such as `constraints/gcp.resourceLocations` (allowed locations), `constraints/gcp.restrictNonCmekServices` (CMEK required) or VPC Service Controls, come from your organization's policies. Choose a permitted location, set an encryption key on the sync, or ask your Google Cloud admin to allow the request.
